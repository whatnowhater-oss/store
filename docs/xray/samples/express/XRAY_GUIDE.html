Codebase X-ray: Express

Sample report. Source: expressjs/express at commit 1c6f1b0 (version 5.3.0), mapped 2026-10-31. Files in this pack: graph.html (open in a browser, click any node), GRAPH_REPORT.md (raw graph stats), and this guide.

The one-minute version

Express 5 is much smaller than most people expect: about 2,800 lines in 6 files under lib/. Most of the work is done by 28 small dependencies. Routing lives in the separate router package, body parsing in body-parser, file serving in send and serve-static, and the final error page in finalhandler. Express itself is the glue: an app function, and the req and res objects with their helper methods. Read express.js, then application.js, then skim response.js.

The core abstractions (most connected in the graph)

  1. res (19 connections), response.js. The response prototype. Every res.* helper is defined on it.
  2. app (17), application.js. The application prototype, mixed into each app function.
  3. sendfile() (9), response.js:924. The shared engine behind res.sendFile and res.download.
  4. req (7), request.js. The request prototype.
  5. View (4), view.js. Template lookup and rendering.

The graph has no import cycles and no links across files that the code doesn't state outright. That is typical of a small, flat library and makes Express safe to change one file at a time.

How a request flows through Express

  1. express() returns a plain function app(req, res, next) that calls app.handle (express.js). That is why an app can be passed straight to http.createServer or mounted inside another app.
  2. app.handle (application.js:152) creates the final handler with finalhandler, sets X-Powered-By if enabled, links req.res and res.req, and creates res.locals.
  3. It swaps the prototypes of Node's request and response objects to app.request and app.response with Object.setPrototypeOf. That single step is what gives req and res all the Express helpers.
  4. It calls this.router.handle(...). The router comes from the router package and is created lazily the first time app.router is read (application.js:69).
  5. The router runs matching middleware and routes in the order they were added. Anything unhandled, including errors passed to next(err), ends at finalhandler, which sends the 404 or error page.

Things that surprise new contributors

  • Routing isn't in this repo. app.get, app.use and app.route mostly forward to the router package. Bugs about path matching usually belong there.
  • Prototype swapping. req and res are Node's own objects with their prototypes replaced. A mounted sub-app swaps them again and restores the parent's prototypes when it calls next (application.js, in app.use).
  • Query parsing is "simple" by default. In Express 5, req.query uses Node's simple parser, so nested objects like a[b]=1 are not expanded unless you set query parser to extended.
  • Settings are inherited. A mounted sub-app inherits the parent's settings through its mount event, unless it set them itself.
  • Defaults worth knowing. x-powered-by is on, ETags are weak, and trust proxy is off, so req.ip is the direct peer until you change it.

Where to make common changes

You want to... Start in
Change a res helper (send, json, redirect, cookie) lib/response.js
Change a req helper or getter lib/request.js
Change app settings or defaults lib/application.js: defaultConfiguration
Change template rendering lib/view.js, app.render, res.render
Change ETag or query parser options lib/utils.js
Change route matching the router package, not this repo

Suggested first week for a new engineer

  1. Day 1: open graph.html and look at how few nodes there are, then read lib/express.js end to end.
  2. Day 2: read app.handle and app.use and trace one request with the flow above.
  3. Day 3: read res.send and res.json in response.js, the most used code in the library.
  4. Day 4: read the router package's handle function to see the other half of the flow.
  5. Day 5: pick a small open issue about a req or res helper.
