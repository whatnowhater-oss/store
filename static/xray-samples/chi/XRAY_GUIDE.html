Codebase X-ray: chi

Sample report. Source: go-chi/chi at commit 9f8adb1 (Go 1.24 module), mapped 2026-10-31. Tests and _examples/ were left out of the map. Files in this pack: graph.html (open in a browser, click any node), GRAPH_REPORT.md (raw graph stats), and this guide.

The one-minute version

chi is a small HTTP router for Go: about 1,850 lines of core code in 5 files, plus 31 optional middleware files (about 2,700 lines) that you can ignore until you need one. Everything is built on the standard library's http.Handler, so there is no custom request type to learn. The core is a Mux that holds a middleware stack and a radix tree of routes, and a Context that carries URL parameters through each request. Read chi.go, mux.go, context.go, then tree.go.

The core abstractions (most connected in the graph)

  1. Mux (40 connections), mux.go:21. The router. Holds the middleware stack, the route tree, a sync.Pool of contexts, and a link to its parent when mounted.
  2. Context (30), context.go:45. Per-request routing state: the URL parameters, the matched pattern and the remaining path for sub-routers.
  3. Router (27), chi.go:68. The interface Mux implements. Program against this.
  4. node (21), tree.go:97. One node of the radix tree. Four kinds: static (/home), regexp (/{id:[0-9]+}), parameter (/{user}) and catch-all (/api/*).
  5. basicWriter (17), middleware/wrap_writer.go. Wraps http.ResponseWriter so middleware can see the status code and bytes written.

How a request flows through chi

  1. Go's HTTP server calls Mux.ServeHTTP (mux.go:63).
  2. If no route was ever registered, it answers 404 straight away.
  3. If a parent router already put a Context on the request, it reuses it. Otherwise it takes one from the pool, resets it and attaches it to the request.
  4. It calls mx.handler, which is the middleware stack wrapped around routeHTTP. Middleware therefore runs before route matching, so it can't know which route will match.
  5. routeHTTP (mux.go:455) picks the path (RawPath if set), maps the method, and calls tree.FindRoute (tree.go:383).
  6. On a match it copies URL parameters into the standard r.SetPathValue, sets r.Pattern, and calls the handler. With no match it answers 405 if the path exists for another method, otherwise 404.
  7. When the handler returns, the Context goes back into the pool.

Things that surprise new contributors

  • Middleware order is enforced. Use panics if called after the first route is added (mux.go:100), because the handler chain is built once at that moment.
  • Middleware runs before matching. To act on the matched route, use With or Group to add middleware to specific routes, or read RoutePattern() after calling next.
  • Contexts are pooled. Don't keep a *chi.Context after the request ends; it will be reset and reused by another request.
  • Mount rewrites the path. A mounted sub-router sees only the rest of the path after the mount point (nextRoutePath). Mount panics if the path is already taken or if you mount a router onto itself.
  • Standard library interop. URL parameters are also set as r.PathValue(...), so code written for Go 1.22+ routing patterns can read them. Handle("GET /x", h) also works because chi splits on the first space.
  • The QUERY method. chi registers the newer HTTP QUERY method alongside the usual ones (tree.go:37).

Where to make common changes

You want to... Start in
Change how paths match or add a pattern type tree.go: InsertRoute, findRoute, patNextSegment
Change 404/405 behaviour mux.go: NotFound, MethodNotAllowed, routeHTTP
Change sub-router mounting mux.go: Mount, nextRoutePath
Read URL parameters differently context.go: URLParam, RouteParams
Add or fix a middleware middleware/ (each file stands alone)
List every route for docs tree.go: Walk

Suggested first week for a new engineer

  1. Day 1: open graph.html, find Mux, and follow its links to node and Context.
  2. Day 2: step through one request from ServeHTTP to your handler with the flow above.
  3. Day 3: read tree.go with a few patterns in mind, such as /users/{id} and /files/*.
  4. Day 4: read Mount, Route and Group, then build a small nested router to watch the path rewrite.
  5. Day 5: read two middleware files, logger.go and recoverer.go, then pick a small open issue.
